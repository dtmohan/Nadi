# Parashari divisional period-lord experiment, version 3

This fixed protocol defines a new experiment before its public-case scores are run. It was motivated by a user-supplied example, so that person's case is not independent validation. Version 2, its manifest, code and published results remain unchanged. Do not change this protocol or tune the weights after viewing the new case scores and still call the same cases independent.

## Rule and sources

For a supported, favourable ordinary marriage, childbirth, or new job/promotion event, start with the six unchanged v2 factors in [the v2 protocol](parashari-specific-v2-protocol.md). The selected chart ayanamsa and node type apply to both versions. V2 already includes partial D1 and divisional support, D1/event-specific period links and event-day transits; its marriage period check already includes some D9 connections. Mixed or unfavourable events, job loss, business, other event types and events before birth remain ineligible under the v2 gate.

Add one Boolean factor for the Vimshottari **mahadasha** lord and one for the **bhukti** lord, in the event's relevant division. Either factor matches if its lord has at least one of the primary links computed in the existing Manley evidence:

1. occupies or fully aspects the event house;
2. is the house lord, conjoins it by sign, or has a full sign aspect with it in either direction; or, for a node, occupies the house lord's sign;
3. is, conjoins, or has a full sign aspect with an event karaka in either direction; or, for a node, occupies the karaka's sign.

The mappings are childbirth: D7, house 5, Jupiter; marriage: D9, house 7, Venus; career: D10, house 10, Sun/Mercury/Jupiter/Saturn. Paul Manley, *Birth Time Rectification: How to Find Your Exact Birth Time* (2022), ch. 4 pp. 101, 118–122, describes these house, lord and karaka clues for divisional-event reasoning. The user's supplied edition is not redistributed in this repository. This is a **partial, app-defined operationalization**, not the book's complete funnel or qualitative judgment. The book distinguishes the quality of placements and aspects; treating each factor as one Boolean point is Nadi's experimental choice. Six v2 factors plus two new Boolean factors = **8 equal points per event**, not a probability. The two added factors can duplicate one another when the main and sub lords are the same, and overlap with v2 marriage factors; disclose this correlation. D1 hints, negative indications and divisional strain remain visible but are not newly scored. Node aspects, indirect chains through node dispositors, all yogas, secondary clues and 3/4/5-level dasha refinements are omitted. A failed rule does not mean the event could not occur.

## Fresh public-case selection

Before scoring, construct a case manifest of at least eight people from diverse locations and backgrounds where feasible. Exclude every individual in the earlier Nadi public-figure, rectification, v1 holdout, and v2 case fixtures, the user-supplied case, and the example subjects used in the supplied Manley book. For a case, require a reported birth date, clock time and place with a cited source independent of any astrological rectification, and at least two distinct, separately dated eligible events. Prefer birth-record sources, then named contemporary family reports; record each source's origin, known conflicts and estimated precision. A time produced by astrological rectification is ineligible as ground truth. Use independently sourced event dates and locations where available, record unknown event clock times, and use local noon in the event zone when absent. Avoid counting twins or two dates describing a single underlying event as independent events. Sources are public quotations of records or recollections, not records inspected by this project.

Select and freeze the manifest before the first case score. List search/source exclusions and conflicts when known; no case is added, removed or tuned because of its result. A convenience sample of public figures and their correlated family events is not representative of the general population. There is no assumption that a reported birth time is correct to the minute.

## Evaluation

Apply the previously fixed [v2 evaluation design](parashari-specific-v2-protocol.md) to v2 and v3 on the same cases and candidate boundaries. Sort each case's distinct eligible event dates; alternating dates are input and held out. Events sharing a day stay together. Compute both sets for segmentation, but rank each version only on its input events. Cases with a single input event are weak and must be identified. Scan ±30 minutes about the published time, with the event instants and time zones fixed in the manifest. Use true exact reported instants in Validate when comparing with the reported chart; do not replace them with a midpoint.

For each version and case, report the complete tied top set, total top coverage of the hour, whether any top interval touches the reported-time ±5-minute band, and the published-time duration-weighted midrank. Do not break ties using distance to the reported time. Report top coverage and ±5-minute touch side by side; also calculate the expanded-top-set geometric reference as in v2. The geometric reference is not an independent probability or p-value. Report ±10-minute touch as a sensitivity to rounded times, not an alternative chosen after seeing results.

For held-out events, compare the score at the reported birth time with the duration-weighted mean across **all** top intervals; normalize by the respective max when summarizing across v2 and v3. Compare each held-out event with six date controls at −180, −120, −60, +60, +120, +180 days, preserving event zone and clock time; exclude pre-birth dates and dates that duplicate a recorded event. These are correlated comparison dates and are not verified non-events. Report actual and control values, unavailable cases and category counts. Also report whether the new factors are constant across an hour, how often both are true and how often they have distinct or duplicate lords, so a high coverage or change in weights is visible.

The [case manifest](../scripts/fixtures/parashari-divisional-v3-cases.json), this protocol, scorer and machine-readable results shall be hashed. Evaluation and unit tests must run before applying the version to the user's chart. Do not claim birth-time accuracy when the test does not support it.
